SSDF Market Report: What Buyers Are Asking For

Sovereign Security Data Fabric · AI/MCP-native SOC and firewall operations · 2026-06-07
Market signal: vendors are converging on “ask natural-language questions over security data,” but the unmet wedge is trusted, local, cross-vendor memory: agents that know rule history, traffic trends, topology, change context, and investigation provenance without exporting raw telemetry to SaaS.

Highest-value asks SSDF should target

1. Explain rule and policy history

“Why does this rule exist, who changed it, what broke after, and is it still used?” Azure Firewall change tracking, PAN rule usage, and policy-management vendors all point to audit trails, rule usage, and change impact as recurring operational needs.

2. Trend traffic and capacity by rule/device

“Show connections/sec, denies, bytes, top apps, and anomalies for this firewall/rule/zone over time.” Palo Alto markets natural-language network questions; operators need this grounded in telemetry, not dashboard spelunking.

3. Find unused, risky, shadowed access

“Which rules are unused, overly broad, shadowed, redundant, expired, or still allowing threats?” PAN documents hit-count-driven cleanup; Cisco highlights shadowed/redundant rules; FireMon/AlgoSec/Tufin sell policy cleanup and risk reduction.

4. Compress investigation context

“Summarize this incident, the entities involved, prior related events, and next queries.” Microsoft Security Copilot and Elastic AI Assistant both center alert investigation, incident response, query generation, and contextual summaries.

5. Turn natural language into safe queries

“Build the KQL/SQL/filter for denied RDP from untrusted zones last week.” Microsoft cites query/script generation; Elastic cites query generation. SSDF’s differentiator is bounded, read-only MCP tools plus guarded SQL.

6. Preserve operational knowledge

“I wish the LLM knew the tribal knowledge: ticket links, exceptions, app owners, maintenance windows, and past decisions.” SOC analysts report too much manual work; Tines found 64% spend over half their time on tedious work and 66% believe much can be automated.

What this means for SSDF direction

  • Lead with firewall/SASE operations, not generic SIEM: rule history + traffic trends + unused/risky access is a sharper wedge than “chat with logs.”
  • Make time-series questions first-class: per rule/device/zone cps, denies, bytes, hit counts, top talkers, deltas before/after change, and anomaly flags.
  • Add provenance memory: connect telemetry to config snapshots, commits, tickets, comments, owners, and MCP actions so agents can answer “why” not just “what.”
  • Stay read-only but action-adjacent: SSDF should recommend and hand off to vendor MCPs; keep its own boundary as sovereign evidence/context fabric.
  • Split local vs frontier outputs: local agents get raw/detail; frontier agents get redacted summaries and aggregates. This maps directly to market sovereignty concerns.

Recommended near-term product package

“Firewall Memory + Metrics MCP.” Tools: explain_rule(rule), rule_traffic_trend(rule, window), unused_rules(), change_impact(change_id), top_policy_risks(), incident_context(entity/window). This package converts SSDF from a log query layer into the agentic memory layer operators are implicitly asking vendors to build.
