SSDF Market Position and Direction

Sovereign Security Data Fabric · MCP-native security context for autonomous agents · 2026-06-07
Positioning: SSDF should be positioned as a minimal, self-hosted, MCP-native security data fabric — not a SIEM, not an XDR, and not a full-stack cybersecurity vendor platform. Its job is to normalize, store, correlate, and safely expose security context to LLM agents under the operator’s control.

Market context

The market is moving toward AI-native security operations, but the dominant approaches create a gap. Elastic provides a mature search/SIEM/XDR platform with rich UI, integrations, detections, and optional AI assistants. Cylake is publicly positioning around a much broader sovereign, vertically integrated cyber platform for regulated institutions, including hardware/software and agentic protection. Both validate the same macro thesis: security is becoming a data-and-AI problem, and sovereignty matters.

SSDF’s opportunity is the narrower but sharper wedge between them: an open, operator-owned data substrate purpose-built for autonomous agents and MCP tools. It can sit beside existing firewalls, SIEMs, and vendor products without trying to replace them immediately.

Against Elastic

Elastic is mature and broad: search, dashboards, SIEM, XDR, endpoint, cases, detections, and cloud/self-managed deployments. SSDF should not compete on UI or feature breadth. It should compete on sovereignty-by-construction, minimal footprint, ClickHouse-first analytics, and MCP as the primary API.

Against Cylake

Cylake is aiming at a complete sovereign cybersecurity platform. SSDF should remain composable: read-only data fabric, swappable components, and separate vendor MCPs for enforcement. This keeps scope tight and makes SSDF useful before it becomes a platform.

Current wedge

  • Concrete first use case: SRX security logs → Vector ECS normalization → ClickHouse → read-only MCP query server.
  • Primary buyer/user: technical security operator, lab builder, regulated operator, or MSP that wants AI-agent workflows without sending raw telemetry to SaaS.
  • Core promise: “Ask agents grounded questions about your security data, locally, safely, and with provenance.”
  • Hard boundary: SSDF does not manage devices. Action is delegated to separate vendor MCPs such as Junos/PAN-OS tooling, preserving a clean data-plane/control-plane separation.

Direction

  • Near term: harden M1/M2: reliable ingest, schema discipline, read-only ClickHouse access, guarded SQL, and agent-friendly query tools.
  • Next sources: add PAN-OS and other real operator-owned systems using ECS-compatible mappings; prove multi-vendor correlation before expanding feature scope.
  • Entity layer: add lightweight asset/identity/application resolution behind a graph seam only when event queries stop being enough.
  • Sovereignty tiering: split local/full-detail agent tools from frontier/redacted tools; enforce least-data responses, audit, and provenance.
  • Longer term: become the agentic security context plane that existing SIEMs, firewalls, and vendor MCPs can consume — not another monolithic console.
Recommended tagline: “A sovereign, MCP-native security data fabric for autonomous agents.”
Strategic discipline: stay small, read-only, composable, and agent-first until real operator workflows pull in additional platform features.
